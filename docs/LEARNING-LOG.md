## 第 0 章 · 整个站的框架（先读这个）

> 先把这张地图记住，后面所有细节都挂在这张图上。

### 一、5 层：数据怎么从数据库走到屏幕

    ① 数据库  →   ② 后端   →   ③ 网络   →   ④ 前端   →   ⑤ 屏幕
      MySQL       Spring        HTTP        app.js      浏览器
      essay 表    Essay 对象    JSON        JS 对象     HTML → 像素

### 二、每一层说哪种"语言"，中间谁翻译

每一层只会说一种话，也只听得懂一种话：

| 层 | 在哪 | 它说的"语言" | 长什么样 |
|---|---|---|---|
| ① 数据库 | MySQL | **SQL**（表 / 行 / 列）| `essay` 表里的**一行** |
| ② 后端 | Spring Boot | **Java**（对象）| 一个 `Essay` **对象** |
| ③ 网络 | HTTP 传输 | **JSON**（文字）| `{"id":1,"title":"…"}` |
| ④ 前端 | 浏览器 | **JavaScript**（对象 / 数组）| `list[0].title` |
| ⑤ 屏幕 | 浏览器渲染 | **HTML / CSS**（标签）| `<article>…</article>` |

**两边"说的话"不一样，中间就必须有翻译：**

| 交接处 | 谁翻译 | 靠什么翻译 |
|---|---|---|
| ① 数据库 ↔ ② Java 对象 | **Hibernate / JPA** | 实体类上的注解：`@Entity`、`@Column(name="written_on")` |
| ② Java 对象 ↔ ③ JSON | **Jackson** | getter 的名字：`getWrittenOn()` → `writtenOn` |
| ③ JSON ↔ ④ JS 对象 | **浏览器** | `res.json()`（文字→对象）、`JSON.stringify()`（对象→文字）|
| ④ JS 对象 ↔ ⑤ HTML | **我写的代码** | `essayHTML()`、`postHTML()`、`postFromApi()` |

> 一句话：**表 → 对象 → JSON → JS 对象 → HTML → 像素，每一步都要翻译。**

### 四、门卫是另一条线（横切过来）

第一节那条链讲的是「**数据的形态怎么变**」；门卫管的是另一件事：「**谁被允许**」。

#### 1. 门口分两半：门外 / 门内

    门 外（不用令牌）                      门 内（必须带令牌）
    ────────────────────                  ──────────────────────────
    输密码 → POST /api/login              PUT    /api/admin/profile
             （在这儿领令牌）              POST   /api/admin/posts
                                         DELETE /api/admin/posts/3
    看内容 → GET /api/essays              GET    /api/admin/whoami
             GET /api/profile
             GET /api/posts

> ⚠️ **登录必须在门外** —— 否则就成了"没令牌就不能登录、不登录就拿不到令牌"的死循环。

#### 2. 先登录拿令牌，之后一直带着

    你输密码
      │
      ▼
    POST /api/login           ← 不带令牌（因为还没有）
      │   后端比对哈希
      ├── 不对 → 401「密码不对」
      └── 对   → 发一张令牌 🎫
      │
      ▼
    前端存进 localStorage      ← 浏览器的小抽屉，关了页面还在
      │
      ▼
    之后每次"写"都带着它：
      PUT /api/admin/profile
      Authorization: Bearer 2afcbd58...
      │
      ▼
    🚪 门卫检查令牌 → 有效放行 / 无效 401

#### 3. 一条规则管住全部门内接口

`WebConfig` 里只有一行：

    .addPathPatterns("/api/admin/**")

→ 以后新接口只要网址以 `/api/admin/` 开头，**自动被守**，门卫一行都不用改。
→ 所以只要记住一条命名约定：**想被保护的接口，网址就写成 `/api/admin/xxx`。**

#### 4. 门卫四件套

    WebConfig             → 排班表：指定守哪条线（/api/admin/**）
    OwnerAuthInterceptor  → 门卫本人：检查每个请求
    OwnerAuthService      → 大脑：发令牌 / 验令牌
    AuthController        → 发放处：登录 / 退出 / whoami

#### 5. 两条线互不干扰

| | 翻译链 | 门卫 / 令牌 |
|---|---|---|
| 管什么 | 数据长什么样（形态怎么变）| 谁被允许做这件事 |
| 方向 | 横向：从数据库一路到屏幕 | 纵向：横切在某一个点上 |
| 关心内容吗 | 关心（要改名、要加工）| 完全不关心（只看令牌）|
| 加一个新接口 | 延长一段 | **不用改**（只要挂在 `/api/admin/` 下）|
| 换令牌方案 | **不受影响** | 要改 |

> **翻译管「怎么搬」，门卫管「准不准搬」。**

### 五、只要记住这 3 句话

| # | 记住这句 | 为什么 |
|---|---|---|
| 1 | **前端要数据 → 先找后端 → 后端再找数据库** | 前端永远不直接碰数据库 |
| 2 | **后端和前端之间，只用 JSON 说话** | JSON 是它们唯一的"接头点" |
| 3 | **谁能"写"，由后端的门卫说了算** | 前端说了不算（改前端代码也没用）|

## 第 1 天 · 2026-09-10

> **📍 今天在框架的哪里**：认识框架本身
> - 角色：4 个都点到（数据库 / 后端 / 前端 / 浏览器）
> - 翻译：还没深入，只知道"三边说的话不一样"
> - 一句话：**先把整张地图建立起来**

**Q：后端是不是前端和数据库之间的桥梁？**
是。前端只会说 JSON，数据库只懂 SQL，**后端是中间那个既懂两边、又握着钥匙的人**。

**Q：请求 / 响应 / 接口是什么？**
- 请求 = 我发出去的一封信（动词 + 地址 + 内容）
- 响应 = 回信（状态码 200 / 401 / 404…… + 内容）
- 接口 = 约定好的窗口：地址 + 用什么动词 + 会还我什么

**Q：门卫是怎么校验身份和权限的？**
密码只发一次（登录）→ 后端发一张令牌 → 之后每次"写"都带上令牌 → 门卫检查。

**Q：我要看懂所有代码吗？**
不用。记住这几个就够：**实体=表、仓库=取数据、控制器=窗口、门卫=查令牌**；框架内部先当黑盒。

## 第 3 天 · 2026-09-12

> **📍 今天在框架的哪里**：角色「后端」+ 第 ① 道翻译
> - 角色：后端
> - 翻译：第 ① 道（数据库 → 后端）—— 后端怎么把请求变成 SQL
> - 一句话：**后端是会讲两种话的中间人**

**Q：门卫是后端做的事吗？**
是，全在后端。前端只负责"把密码发过去、把令牌存起来"。

**Q：前端拿到 token，就等于允许连接数据库了吗？**
不是，这是两件事：
- **连接数据库**：后端启动时就一直连着（和令牌无关）
- **令牌**：只决定"这次操作允不允许做"

一句话：**数据库的门，后端一直开着；令牌管的是"谁有权让后端替他做事"。**

**Q：后端会把前端发来的 JSON 翻译成 SQL 吗？**
会，而且是两段翻译：
`JSON →（Jackson）→ Java 对象 →（Hibernate）→ SQL`

**Q：用了 JPA 就不用 SQL 了吗？**
不是不用，是**不用我亲手写**。JPA 照样生成 SQL 发给 MySQL，只是这句 SQL 由它替我写了。

**Q：接下来是不是就是建各种表，重复"把随笔接进数据库"那件事？**
是。同一套配方换内容：**表的设计图 → 仓库 → 窗口**；写接口挂在 `/api/admin/` 下，自动被门卫保护。

**Q："写接口"是什么意思？**
就是"**拿到令牌之后，真正去改数据库**"的那几个接口：
`POST /api/admin/essays`（新增）· `PUT /api/admin/essays/{id}`（修改）· `DELETE /api/admin/essays/{id}`（删除）

> - 角色：数据库
> - 翻译：第 ① 道（表和对象怎么对应）
> - 一句话：**三张表怎么设计**；以及"谁能改谁的数据"这件事

**Q：后端这么多表，都已经接好了吗？**
一开始只有 `essay`（随笔）走通了全程。今天补上另外两张：
- `profile` —— 我的资料，**永远只有一行**（名字 / 一句话 / 简介 / 头像和背景图的路径）
- `post` —— 发帖（标题 / 正文 / 标签 / 日期）

还差一张可选的 `owner_token`（把令牌存进数据库，重启后端就不用重新登录）。

**Q：什么叫做水平越权（IDOR）？我们是在哪里处理的？**
IDOR = **同样是普通用户，却动了别人的数据**。
最典型的场景：网址里带一个 id，把它改个数字就看到了别人的私密内容：

```
GET /api/memos?userId=1   →（改成）→   GET /api/memos?userId=2
```

根因只有一句：**后端相信了前端说的"我是谁"**。

处理它的是**上一个项目（Cyber-Tunnel）**，不是这个网站：
- 改前：前端传 `userId`，后端照着查 → 改数字就能越权
- 改后：后端签发令牌 → 从令牌里推出**真实的 userId** → 每次查询都加归属条件（`findByIdAndUserId`）
- 记录在那边仓库的 `docs/AUTH-SECURITY.md`

分清两件事（很容易混）：

| | 管什么 | 在哪 |
|---|---|---|
| 认证 / 授权（门卫） | 你是不是站长、**能不能写** | 这个网站：`/api/admin/**` |
| 归属校验（防 IDOR） | **这条数据是不是你的** | Cyber-Tunnel：`findByIdAndUserId` |

这个网站只有一个作者，所以暂时**不需要**归属校验；以后加了"访客留言"或变成多用户，就必须加。

### 谁负责哪一段翻译

| 翻译段 | 谁翻译 | 什么时候定的 | 怎么定的 |
|---|---|---|---|
| 数据库 ↔ Java 对象 | Hibernate / JPA | 以前（另一台电脑）| `@Column(name = "written_on")` |
| Java 对象 ↔ JSON | Jackson | 以前（另一台电脑）| getter 名字自动推导 |
| JSON ↔ 页面要的数据 | 我（前端）| 今天 | `postFromApi()` |
| 页面数据 ↔ HTML | 我（前端）| 前几步 | `postHTML()` / `essayHTML()` |
| HTML ↔ 像素 | 浏览器 | — | 内置 |

### 接口的"接头点"是什么时候定的

接头点 = JSON 里有哪些字段、叫什么、什么类型。

它**不是专门设计的，是写后端实体类时顺手定下的**：

| 接头点的内容 | 由什么决定 |
|---|---|
| 有哪些字段 | Java 类的字段（`Post.java` 里写了 title / body / tags / publishedAt …）|
| 字段叫什么 | getter 的名字（`getPublishedAt()` → `publishedAt`）|
| 字段什么类型 | Java 类型 + Jackson 规则（`LocalDate` → `"2026-09-12"`）|

两边都是"顺手"定的，**谁也没对账**：

    后端：写 Post.java 时定的   →  publishedAt / body / tags(字符串)
    前端：写 postHTML() 假数据时定的 →  date / excerpt / tags(数组)
    → 今天一对账，发现对不上，才写了 postFromApi()

教训：接口清单只记了"地址 + 动词"，没记"返回什么形状"，所以对不上账。
以后加新接口，要把**返回的字段名和类型**也记下来。

接口只约定"接头点"长什么样，不管两边内部各自怎么翻译：

          【后端的地盘】                        【前端的地盘】
  MySQL ──► Java 对象 ──► JSON ═╗      ╔═ JS 对象 ──► 页面数据 ──► HTML ──► 屏幕
         ↑            ↑          ║      ║       ↑              ↑
   @Column(name)    getter       ╚══════╝  res.json()    postFromApi()
     （以前定）     （以前定）     接头点（接口）        （今天定）
                              "长这样、叫什么"

以前定的是：接头点 + 后端那半段。
今天定的是：前端这半段。

### 为什么会有翻译 / 怎么减少

问题不是"没给字段起名"，而是"两边各起各的，没对账"：

    前端（写 postHTML 假数据时）：date / title / excerpt / tags
    后端（写 Post.java 时）：     publishedAt / title / body / tags / createdAt / id

如果当初先把接头点定下来（比如就定成 publishedAt / body / tags），
让两边都照它写，那么 publishedAt → date 这种【改名】的翻译就能省掉。

但差异有三类，只有第一类能靠约定省掉：

| 差异类型 | 例子 | 约定能省掉吗 |
|---|---|---|
| 改名 | `publishedAt` → `date` | 能省 |
| 加工 | `body`（全文）→ `excerpt`（摘要）| 省不掉：数据库里没有 excerpt 这个字段，必须算出来 |
| 显示格式 | `2026-09-14` → `2026 · 09 · 14` | 省不掉：这是"长什么样"的问题，通常留在前端 |

结论：约定能省掉"改名"，省不掉"加工"和"显示格式"。
那不是名字问题，是活儿总得有人干。

翻译由谁做，三种选择：

| 做法 | 谁翻译 | 好处 | 代价 |
|---|---|---|---|
| 前端加适配层（现在这样）| 前端 | 后端干净，返回真实数据 | 前端多一层 |
| 后端按前端要的返回 | 后端 | 前端零翻译 | 后端被前端绑死，换界面就得改后端 |
| 先约定统一契约 | 两边 | 省掉"改名"那类翻译 | 要先沟通、先写文档 |

业界主流是"先约定契约 + 各自翻译"。
契约可以是一份 docs/API.md，记清每个接口返回的字段名和类型。
（现在 代码结构.md 只记了"地址 + 动词"，没记"返回什么形状"，所以才会对不上账。）

### 翻译 vs 复用（两个独立的概念）

| | 翻译（适配）| 复用 |
|---|---|---|
| 定义 | 一种形状 → 另一种形状 | 一份数据 → 喂给多个地方 |
| 为什么需要 | 两边的说法不一样 | 多个地方要显示同一样东西 |
| 例子 | `postFromApi()`、日期格式化 | `drawHome` / `drawAll` 共用 `POSTS` |

发帖功能两样都需要：

    后端 JSON
        │  postFromApi()       翻译 1 次
        ▼
    一份数据 POSTS
        ├──► drawHome()       首页「近期发帖」
        └──► drawAll()        「发帖」页

反证：随笔页只有 1 个使用者，也照样需要翻译。
所以翻译不是"页面多"造成的，而是"两边说法不同"造成的。

### 分层

发帖这条链现在是 4 层，每层只干一件事：

    后端 JSON
        │  翻译层   postFromApi()      只管数据长什么样
        ▼
    页面要的数据 { date, title, excerpt, tags }
        │  渲染层   postHTML()         只管数据怎么变成 HTML
        ▼
    HTML 文字
        │  插入层   innerHTML =
        ▼
    屏幕

好处：
1. 改动不扩散：后端改字段名，只改翻译层 1 行
2. 好排查：数据不对查翻译层，样式不对查渲染层
3. 可复用：同一套渲染函数，换个容器就能用在别处

### 为什么一段文字会变成两个段落

数据库里没有"段落"，只有一串字符，中间夹着两个看不见的换行符（`\n`）。

    "…读数据了。\n\n它还顺便…"
                  ↑↑ 两个换行符，看不见，但占位置

两个换行符 = 一个空行（跟记事本里按两次回车一样）。

但 HTML 会把换行吃掉：连续的空白（空格 / 换行 / Tab）都只当作一个空格。

    <p>
      第一行
      第二行
    </p>
    → 渲染成：第一行 第二行

所以在网页上换行 / 分段必须靠标签：

| 标签 | 效果 | 用在哪 |
|---|---|---|
| `<br />` | 换行（同一段之内）| 「关于我」的简介 |
| `<p>` | 分段（新的一段，上下有间距）| 「随笔」的正文 |

完整流程：

    ① 数据库：  "…\n\n…"                     1 条字符串，含 2 个换行符
          │  split(/\n\s*\n/)                剪开
          ▼
    ② 数组：   ["第一段", "第二段"]            2 个元素
          │  map(每块包一层 <p>)              穿衣服
          ▼
    ③ 数组：   ["<p>第一段</p>", "<p>第二段</p>"]
          │  join('')                        粘回去
          ▼
    ④ 字符串： "<p>第一段</p><p>第二段</p>"
          │  innerHTML =
          ▼
    ⑤ 屏幕：   两个有间距的段落

数据库只管存字符，排版是前端用标签做出来的。

### split / map / join

| 工具 | 干什么 | 输入 → 输出 | 例子 |
|---|---|---|---|
| `split` | 按"刀口"剪开 | 字符串 → 数组 | `"A-B".split("-")` → `["A","B"]` |
| `map` | 逐个加工 | 数组 → 新数组 | `[1,2].map(n => n*2)` → `[2,4]` |
| `join` | 粘起来 | 数组 → 字符串 | `["A","B"].join("")` → `"AB"` |

注意：map 里写函数名，不加括号。
`map(essayHTML)` 对，`map(essayHTML())` 错（加了括号就是立刻执行，然后报错）。
因为是把"这台机器"交给 map，不是现在就开机。

为什么最后要 join：innerHTML 只接受一个字符串，不吃数组。

### split 的刀口为什么写 /\n\s*\n/

| 符号 | 意思 | 为什么要 |
|---|---|---|
| `\n` | 一个换行 | 必须有 |
| `\s*` | 零个或多个空白（空格 / Tab）| 防止有人在空行里多敲了空格 |
| `\n` | 又一个换行 | 必须有 |

合起来 = 空行。
只写 `/\n\n/` 切不了 "⏎   ⏎" 这种；`\s*` 是防御性写法。

### 重启电脑后连不上后端

| 东西 | 启动方式 | 重启后 |
|---|---|---|
| MySQL | Windows 服务（开机自启）| 自动起来 |
| 后端 Spring Boot | 手动跑的临时进程 | 没了 |

所以每次重启电脑后，双击 `D:\myworks\start-backend.bat`。
看到 `Started SiteServerApplication` 才算启动成功。窗口不能关。

排查顺序：

    1. 浏览器打开 http://localhost:8080/api/profile
         打不开 → 就是后端没开
    2. 看 start-backend.bat 的窗口有没有报错
    3. 确认看到 Started SiteServerApplication

编码（字符 ↔ 字节）出错。
按 UTF-8 写、按 GBK 读 → 规则对不上 → 乱码。

### 门卫四件套

      ┌────────────────────────────────────────┐
      │   WebConfig  ·  排班表                  │
      │   "门卫，你守 /api/admin/** 这条线"      │
      └───────────────────┬────────────────────┘
                          │ 把门卫安排到岗位上
                          ▼
      ┌────────────────────────────────────────┐
      │   OwnerAuthInterceptor  ·  门卫本人      │
      │   每个 /api/admin/** 请求，先过我这一关   │
      └───────────────────┬────────────────────┘
                          │ 问一句："这令牌有效吗？"
                          ▼
      ┌────────────────────────────────────────┐
      │   OwnerAuthService  ·  大脑 / 档案柜     │
      │   管密码哈希、发令牌、验令牌              │
      └────────────────────────────────────────┘

      ┌────────────────────────────────────────┐
      │   AuthController  ·  发放处              │
      │   登录 / 退出 / whoami                  │
      └────────────────────────────────────────┘

| 文件 | 它的角色 | 一句话 |
|---|---|---|
| `OwnerAuthService` | 大脑 / 档案柜 | 管密码哈希、发令牌、验令牌、作废令牌 |
| `OwnerAuthInterceptor` | 门卫本人 | 每个 `/api/admin/**` 先过它：有令牌放行，没令牌 401 |
| `WebConfig` | 排班表 | 告诉 Spring：门卫守哪条线（`/api/admin/**`）|
| `AuthController` | 发放处 | 3 个窗口：登录 / 退出 / whoami |

两个要记住的设计：

1. 门卫只管"你有没有令牌"，**不管你要改什么**
   → 以后加多少写接口，门卫一行都不用改
2. `preHandle` 返回 `false` = 请求在这里就终止
   → 业务代码根本不跑，数据库更碰不到（"在入口就拦住"）

### 令牌是什么

| 问题 | 答案 |
|---|---|
| 令牌是多变的吗 | **是**。每次登录都用 `UUID` **随机生成一张新的**，两次一定不一样 |
| 存在数据库里吗 | **不在**。存在后端程序的**内存**里（一张"令牌 → 过期时间"的表）|
| 那会怎样 | 后端一重启，内存清空 → **所有令牌作废** → 要重新登录 |

- 为什么必须随机：如果令牌能猜出来，别人猜到就能假装是站长
- 为什么现在放内存：够用、简单
- 放数据库的好处：重启不掉线、能"踢某台设备下线" —— 这是以后的优化项

### 两种走法

**没带令牌：**

    前端 PUT /api/admin/profile     （请求头里没有 Authorization）
      → 排班表说这条线有门卫
      → 门卫取 Authorization → null → isValid(null) → false
      → 写 401 + {"message":"需要站长令牌"} → return false
      → 请求就此结束，Controller 一行没跑

**带了有效令牌：**

    前端 PUT /api/admin/profile     Authorization: Bearer 2afcbd58...
      → 排班表说这条线有门卫
      → 门卫取到令牌 → isValid(token) → true → 放行
      → 这才轮到 Controller 干活 → 改数据库

### 一个重要认识：这是两个不同维度的东西

    ①数据库 → ②Java对象 → ③JSON → ④JS对象 → ⑤页面数据 → ⑥屏幕
                            ▲
                            │
                        🚪 门卫横切在这里
                      （请求刚进后端，业务还没跑）

| | 翻译链 | 门卫 / 令牌 |
|---|---|---|
| 管什么 | 数据长什么样（形态怎么变）| 谁被允许做这件事 |
| 方向 | 横向：从数据库一路到屏幕 | 纵向：横切在某一个点上 |
| 回答的问题 | "信息怎么从 A 变成 B" | "这个动作能不能做" |
| 关心内容吗 | 关心（要改名、要加工）| 完全不关心（只看令牌）|

两者**互相垂直**，可以各自变化：

| 变化 | 翻译链 | 门卫 |
|---|---|---|
| 加一个新接口 | 延长一段 | **不用改**（只要挂在 `/api/admin/` 下）|
| 换一套令牌方案（比如存进数据库）| **不受影响** | 改 |

**一句话：翻译管「怎么搬」，门卫管「准不准搬」。**

## 第 8 天 · 2026-09-17

### 今天做了什么

**发帖和随笔现在都能配图了（可以多张）。** 流程是：

    选图 → 立刻传给后端存盘（后端回一个路径）→ 点保存时只把"路径列表"跟正文一起发过去

为什么"选完就传"而不是"保存时一起传"：用户马上能看到缩略图；保存那一步只发一次 JSON，不会出现"正文存了、图没存"的半截状态。

### 图片为什么不放进数据库

数据库里只存**路径**，文件躺在硬盘上：

    数据库：  image.path = "uploads/2026/09/abc.png"
    硬盘上：  server/uploads/2026/09/abc.png
    网址上：  http://localhost:8080/uploads/2026/09/abc.png
              ↑ WebConfig 把硬盘目录"挂"到了这个网址（addResourceHandlers）

三个理由：数据库存二进制又大又慢；图片要能被浏览器当普通文件直接读；备份/搬家时可以分开处理。

### 一张表管两种内容（owner_type）

    image 表： owner_type="post"  + owner_id=5  → 第 5 条帖子的图
               owner_type="essay" + owner_id=3  → 第 3 篇随笔的图

好处：帖子和随笔**共用一套**上传/删除代码，不用写两遍。这张表的 id 是自增的，`sort_order` 决定图片先后。

### images 的三种发法（最容易搞混的地方）

| 保存时你怎么发 | 结果 |
|---|---|
| **不带** `images` 字段 | 图片**不动** |
| `"images": []` | **清空**这条内容的图 |
| `"images": ["a.png","b.png"]` | **整条替换**（顺序照你给的来） |

→ 所以"改一条帖子时想加一张图"，要把**老图一起带上**。前端的做法是：读数据时另存一份原样数据，保存时整条发回去。

### 新学到的一招：接口的形状不一定要跟表一样（View）

后端实体 `Post` 里**没有** `images` 这个字段（图在另一张表里）→ 于是另写一个 record 专门描述"接口还给前端的样子"：

    Post.java（表的样子）  +  image 表（图）  ──►  PostView.java（接口的样子）

好处：表怎么改不用牵连接口，接口怎么改不用动表。今天新增的文件：`PostView` / `EssayView` / `Image` / `ImageRepository` / `ImageService` / `UploadController`。

### 前端两个新东西

1. **`imgUrl(path)`**：后端给的是相对路径 `uploads/2026/09/x.png`，`<img>` 要的是 `http://localhost:8080/uploads/...` —— 翻译一次，别处都不用管。（**翻译层**又一次出场）
2. **传文件时不能自己写 `Content-Type`**：浏览器要往这个头里塞一段"边界字符串"来分隔文件，我们自己写了反而把它搞坏。所以 `authFetch` 里加了一句判断：是 `FormData` 就交给浏览器。

### 踩过的坑

- `.ps1` 里不能写中文 —— 老坑又踩了一次（PowerShell 5.1 按 GBK 读，中文会把语法拆坏）。
- 无头测试里"选文件"要自己造：`new DataTransfer()` → `dt.items.add(new File([字节], 'x.png', {type:'image/png'}))` → 塞进 `input.files` → 手动 `dispatchEvent(new Event('change'))`。
- 测试里点删除会被浏览器的确认框挡住 → 先把 `window.confirm = function () { return true; }`。

### 验证结果（这次挺硬）

- 后端 20 项：没令牌 = **401**；传 `.txt` 被拒；传 6MB 被拒；存盘 + `/uploads/**` 读回来 200；帖子和随笔都带上了图；`PUT images=[]` 清空、不带则不动；删内容连带清掉图片记录；测试数据 0 残留。
- 前端 12 项：缩略图真的加载出来了（`naturalWidth > 0`）、✕ 能删、保存后列表里的图也加载出来了、随笔的选图区一样能用。
