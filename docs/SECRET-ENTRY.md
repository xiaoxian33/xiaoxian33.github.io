# 🔐 隐藏管理模式设计说明（Cheat Code Admin）

> 灵感来自游戏里的作弊码：访客看到的是一台普通的赛博电脑，而作者敲一串指令，就能打开"根权限"。
> 本文记录这个设计的**目标、做法、安全边界**，以及它在我面试时能怎么讲。

---

## 一、要解决的问题

个人网站有个尴尬处境：

- 我需要一个"能发内容、能改内容"的管理入口；
- 但访客不该看到一个"登录框"——那会瞬间把作品集变回简历模板，也暴露了站点的结构；
- 而且我主要在**电脑**上写东西，手机端暂时不需要管理能力。

所以我要的不是"更隐蔽的登录页"，而是**根本不存在登录页**。

---

## 二、三道关卡

### 关卡 1：秘密开门（PC 组合键）

站点上**没有任何按钮、链接指向管理入口**。要打开它，只能靠键盘暗号：

| 暗号 | 定义位置 |
|---|---|
| `Ctrl` + `Shift` + `O` | `assets/js/secret.js` 的 `TRIGGER` 常量 |
| `` ` ``（波浪键，输入框外按下） | `assets/js/secret.js` 的 `WAVE_KEY` |

按下后弹出一个**像素终端窗口**，标题是 `???`——不是"管理员登录"，看起来就是一个游戏彩蛋：

```
CYBER-OS · 未知设备已接入
安全通道已打开。本设备身份：未经验证
输入 help 查看我能做什么。
guest@cyber-os:/$ <在这里输入>
```

### 关卡 2：静默输入（连报错都不说人话）

终端支持的命令中，真正用于接入的是：

```
root <主人密钥>
```

关键在于**失败时的反馈**：

- 输错 → 只回一句 `command not found: root`
- 未接通后端 → 只回一句 `tunnel offline. 通道尚未接通。`
- **绝不出现**「密码错误」「登录失败」「权限不足」这类提示

访客就算误触了彩蛋，也只会以为"这网站有个没做完的终端玩具"，联想不到这是管理入口。

### 关卡 3：同页变身（不跳转、不留痕）

密钥校验通过后，**不跳转到任何"后台页面"**，而是在当前页面上添加一个状态类：

```js
document.body.classList.add('is-owner');
```

CSS 里所有与该状态相关的样式**只在解锁后才生效**（例如任务栏版本号后面多出 `● ROOT`）。访客的浏览器里永远不会进入这个状态，因此他们看不到任何编辑按钮、编辑角标——不是"藏起来了"，而是**根本不存在**。

## 三、⚠️ 安全边界（这一段才是面试真正想听的）

**隐蔽不等于安全。** 这个设计只解决"体面"，不解决"防破解"：

| 手段 | 是否算安全措施 | 说明 |
|---|---|---|
| 组合键彩蛋 | ❌ | 打开 DevTools 读一遍 `secret.js` 就能知道暗号 |
| 终端静默失败 | ❌ | 属于"让人不起疑"，不是防护 |
| **后端令牌校验** | ✅ | **写接口必须携带有效设备令牌，否则一律 401/403** |
| **主人密钥哈希存储** | ✅ | 数据库只存 BCrypt 哈希，拖库也反推不出原钥 |
| **失败限流** | ✅ | 连续输错 N 次锁定一段时间，抵御爆破 |
| **HTTPS 传输** | ✅ | 密钥绝不走明文（ngrok 免费域名自带 TLS） |

原则一句话：

> **钥匙（前端入口）可以藏在任何地方，但锁（后端校验）必须写在门上。**

任何一条"只有前端在做校验"的写法都是假安全。前端能藏的是**入口**，后端守的是**数据**。

## 四、主人密钥 + 设备令牌（M4 要落地的方案）

因为本站作者只有我一个人，不需要注册、不需要用户表，只需两层：

```
第 1 层：主人密钥（跨设备）
   一串高熵随机字符串，只存在我的密码管理器里，不绑定任何设备。
   任何新设备第一次接入时输入一次即可 → 这就是"换设备后怎么认出是我"的答案：
   服务器不认识设备，只认凭证；凭证由我随身携带。

第 2 层：设备令牌（单设备 · 隐式登录的手感）
   校验通过后，服务器签发一个长期设备令牌，浏览器保存。
   之后这台设备每次接入都自动带上它 → 免输入直接进入编辑态。
   支持「查看已登录设备 / 踢掉某台」，以应对设备丢失。
```

配套的接口规划：

| 方法 & 路径 | 权限 | 说明 |
|---|---|---|
| `POST /api/owner/login` | 公开（需密钥） | 校验主人密钥 → 签发设备令牌 |
| `GET /api/posts` | 公开 | 学习手账列表（访客只读） |
| `POST/PATCH/DELETE /api/posts` | 仅主人 | 发 / 改 / 删手账 |
| `POST /api/uploads` | 仅主人 | 上传图片 |
| `DELETE /api/owner/devices/{id}` | 仅主人 | 踢掉某台设备 |

## 五、面试常见追问（预演）

**Q：你这个"隐藏后台"是不是 security by obscurity？**
> 隐藏入口那一层是，而且是**故意**的——它解决的是产品体验（访客不该看到登录框），我从设计之初就把它和真正的防护分开了。真正的防护是后端的令牌校验、密钥哈希与失败限流；就算有人读到源码知道了组合键，他也进不来，因为写接口不认"我知道暗号"，只认"你有没有有效令牌"。

**Q：为什么用设备令牌而不是每次输密钥？**
> 因为安全性和便利性要做取舍。密钥是根凭证，泄露代价大，所以我让它尽量少出现在网络上（只在首次接入时传一次，且走 HTTPS）；日常操作使用可随时吊销的设备令牌，丢设备就踢掉那一台，损失可控。

**Q：为什么不用 JWT / Spring Security？**
> 和我在 Cyber-Tunnel 里的取舍一样：先用轻量方案把手写认证链路（签发 → 校验 → 拦截器 → 上下文）跑透，保证每一步都讲得清楚；这个项目后续会平滑升级到 Spring Security + JWT，业务代码不需要大改。个人站点并发极低，数据库存令牌完全够用。

**Q：如果有人在公共电脑上解锁了怎么办？**
> 后台提供"已登录设备"列表，可以一键踢掉；此外设备令牌带最后活跃时间，长期不用的会被清理。
